# Отчёт о развёртывании приложения в Kubernetes

## 1. Описание приложения

Climate Store — учебное клиент-серверное приложение интернет-магазина кондиционеров.

Приложение состоит из следующих компонентов:

- frontend на React и Vite;
- nginx для раздачи собранного frontend и проксирования API-запросов;
- backend на Express и TypeScript;
- PostgreSQL для хранения товаров, производителей и категорий;
- Drizzle ORM для взаимодействия backend с базой данных и выполнения миграций.

Приложение развёрнуто в локальном однодовом кластере Kubernetes, созданном с помощью Minikube. В качестве драйвера Minikube используется Docker.

## 2. Docker-образы

Для frontend и backend используются отдельные многостадийные Dockerfile.

Образ backend:

```text
climate-store-backend:1.0
```

На стадии сборки TypeScript компилируется в JavaScript. Итоговый контейнер запускает production-версию Express-приложения.

Образ frontend:

```text
climate-store-frontend:1.0
```

На стадии сборки создаётся production-сборка React-приложения. В итоговом контейнере nginx раздаёт статические файлы и перенаправляет запросы `/api` на backend.

Локальные образы загружены в Minikube командами:

```bash
minikube image load climate-store-backend:1.0
minikube image load climate-store-frontend:1.0
```

В манифестах используется `imagePullPolicy: IfNotPresent`, поэтому Kubernetes использует локально загруженные образы и не пытается скачать их из внешнего registry.

## 3. Использованные абстракции Kubernetes

### Namespace

Все ресурсы приложения размещены в Namespace `climate-store`.

Namespace логически отделяет ресурсы приложения от системных компонентов Kubernetes и других учебных нагрузок.

### ConfigMap

ConfigMap `climate-store-config` хранит нечувствительные настройки backend:

- `NODE_ENV`;
- `PORT`.

Конфигурация передаётся контейнеру backend через переменные окружения.

### Secret

Secret `climate-store-secret` хранит настройки PostgreSQL:

- имя базы данных;
- имя пользователя;
- пароль;
- строку подключения `DATABASE_URL`.

Secret используется контейнерами PostgreSQL, backend и Job миграции.

В учебной конфигурации применяются демонстрационные учётные данные. В production-среде секреты не должны храниться в репозитории в открытом виде.

### StatefulSet

PostgreSQL запускается с помощью StatefulSet `postgres`.

StatefulSet выбран, поскольку PostgreSQL является компонентом с состоянием. Он создаёт Pod с предсказуемым именем `postgres-0` и подключает к нему постоянное хранилище.

Количество реплик PostgreSQL равно одной. Простое увеличение количества реплик базы данных без настройки репликации не используется.

### PersistentVolumeClaim

Для данных PostgreSQL применяется PersistentVolumeClaim:

```text
postgres-data-postgres-0
```

Запрошенный объём хранилища — `1Gi`, режим доступа — `ReadWriteOnce`.

PVC позволяет сохранить данные при удалении или пересоздании Pod PostgreSQL.

### Deployment

Frontend и backend запускаются с помощью Deployment.

Deployment выполняет следующие функции:

- создаёт ReplicaSet;
- поддерживает необходимое количество Pod;
- пересоздаёт отказавшие Pod;
- поддерживает горизонтальное масштабирование;
- выполняет постепенное обновление контейнеров.

В исходных манифестах frontend и backend запускаются с одной репликой. Во время демонстрации количество реплик увеличивается до трёх командой `kubectl scale`.

### Service

В приложении используются три Service.

`postgres` имеет тип `ClusterIP` и предоставляет PostgreSQL по внутреннему адресу:

```text
postgres:5432
```

`backend` имеет тип `ClusterIP` и предоставляет Express API по внутреннему адресу:

```text
backend:3000
```

`frontend` имеет тип `NodePort` и предоставляет nginx и React-приложение за пределами кластера.

Service выбирают Pod по labels и сохраняют стабильный адрес независимо от пересоздания и количества Pod.

### Job

Job `climate-store-db-init` выполняет одноразовые административные операции:

1. применение миграций Drizzle;
2. заполнение базы демонстрационными данными.

После успешного выполнения Pod Job переходит в состояние `Completed`.

### Readiness Probe

Readiness-пробы определяют, готов ли контейнер принимать запросы.

Для PostgreSQL используется команда `pg_isready`. Для frontend и backend выполняются HTTP-запросы.

Пока проверка не пройдена, Service не направляет запросы в соответствующий Pod.

### Liveness Probe

Liveness-пробы проверяют, продолжает ли контейнер работать. При постоянной ошибке Kubernetes перезапускает контейнер.

### Resources

Для контейнеров указаны `requests` и `limits` по процессору и памяти.

`requests` используются планировщиком Kubernetes при выборе узла. `limits` ограничивают максимальное потребление ресурсов контейнером.

## 4. Взаимодействие сервисов

Пользователь открывает frontend через Service типа NodePort. В Minikube с Docker-драйвером доступ предоставляется командой:

```bash
minikube service frontend -n climate-store --url
```

Последовательность обработки запроса:

```text
Браузер
→ Service frontend
→ Pod frontend с nginx
→ Service backend
→ Pod backend с Express
→ Service postgres
→ Pod postgres
→ PersistentVolume
```

React обращается к относительному адресу `/api`.

Nginx frontend перенаправляет запросы `/api` на:

```text
http://backend:3000
```

Имя `backend` разрешается внутренним DNS Kubernetes в адрес Service backend.

Backend получает строку подключения `DATABASE_URL` из Secret и подключается к PostgreSQL через адрес:

```text
postgres:5432
```

Service распределяют запросы между готовыми Pod, соответствующими их selectors.

## 5. Масштабирование

Frontend и backend являются stateless-компонентами и могут быть масштабированы горизонтально.

Для увеличения количества реплик используются команды:

```bash
kubectl scale deployment/backend --replicas=3 -n climate-store
kubectl scale deployment/frontend --replicas=3 -n climate-store
```

После масштабирования соответствующие Service автоматически начинают распределять запросы между тремя Pod.

Проверка выполняется командой:

```bash
kubectl get deployments,pods -n climate-store
```

PostgreSQL таким способом не масштабируется, поскольку для нескольких экземпляров базы требуется отдельная настройка репликации.

## 6. Результат

Приложение успешно развёрнуто в однодовом кластере Minikube.

Frontend, backend и PostgreSQL находятся в работоспособном состоянии. Миграции и демонстрационные данные применяются через Kubernetes Job. Данные PostgreSQL сохраняются в PersistentVolume. Frontend и backend поддерживают масштабирование до нескольких реплик.
