# ЛР8 — Стратегии развёртывания Climate Store

Я проверил пять стратегий обновления backend каталога в Minikube. Backend работает в двух репликах, хранит данные в PostgreSQL и использует readiness и liveness на `/health`. Заголовки `X-App-Version` и `X-App-Instance` показывают, какая версия и какой под ответили. Версия и экземпляр также записываются в HTTP-лог. Для эксперимента обе версии используют один образ `climate-store-backend:1.6` и различаются значением `APP_VERSION`.

| Стратегия | Что сделал | Результат |
| --- | --- | --- |
| Rolling | Поменял `APP_VERSION` с `v1` на `v2` в Deployment `backend`. Kubernetes заменял поды с `maxSurge: 1`, `maxUnavailable: 0`. | В логе запросов появились новые имена подов и ответы `v2`. |
| Blue/Green | Поднял `backend-green` с `v1` рядом с работающей `v2`. Поменял сервис назначения в HTTPRoute, затем вернул прежний. | Клиент увидел переход `v1 → v2 → v1`. |
| Canary | Установил веса `v1/v2` 90/10, 50/50 и 0/100. Сделал по 100 запросов. | Получил 90/10, 49/51 и 0/100 ответов соответственно. Все 300 ответов были HTTP 200. |
| A/B | Настроил отдельное правило для `x-user-group: beta`. | Обычный запрос вернул `v1`, запрос с заголовком — `v2`. Оба HTTP 200. |
| Shadow | Направил клиентский запрос на `v1`, включил `RequestMirror` на `v2`. | Клиент получил HTTP 200 от `v1`, та же метка `shadow-1795368454` появилась в логе `v2`. Маршрут ограничен GET-запросом каталога. |

К каждой стратегии приложены запись экрана и вывод терминала.
