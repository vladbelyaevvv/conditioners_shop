# Отчёт по проекту «Climate Store»

## Доменная область

Climate Store — учебное клиент-серверное приложение для ведения каталога и продажи кондиционеров. Покупатель может просматривать каталог, фильтровать товары и открывать подробную карточку кондиционера. Сотрудник магазина использует административный раздел для создания, просмотра, изменения и удаления товаров, производителей и категорий.

В первой версии отсутствуют регистрация, авторизация, корзина, оформление и оплата заказов. Это осознанное ограничение MVP: реализована основа каталога и обязательные CRUD-операции. Архитектура допускает добавление пользователей, корзины и заказов в следующих заданиях.

## Стек реализации

### Frontend

- React и TypeScript;
- Vite для разработки и production-сборки;
- React Router для клиентской маршрутизации;
- TanStack Query для загрузки, кеширования и обновления серверных данных;
- React Hook Form и Zod для форм и валидации;
- CSS Modules для изолированных стилей компонентов.

### Backend

- Node.js и TypeScript;
- Express для REST API по HTTP/1.1;
- Zod для проверки параметров, query string и тела HTTP-запросов;
- Drizzle ORM и Drizzle Kit для типобезопасных запросов и миграций;
- PostgreSQL в качестве СУБД.

### Инструменты разработки и качества

- Vitest для модульных тестов;
- npm workspaces для управления frontend и backend из корня проекта.

Docker Compose и Nginx также присутствуют в исходном коде как дополнительный способ запуска и задел для следующих домашних заданий.

## Основные сущности

### Product (кондиционер)

Содержит название, модель, описание, цену, мощность охлаждения, рекомендуемую площадь, класс энергоэффективности, остаток, URL изображения и ссылки на производителя и категорию.

### Brand (производитель)

Содержит название, уникальный slug и страну происхождения. Один производитель может иметь много кондиционеров.

### Category (категория)

Содержит название, уникальный slug и описание. Одна категория может включать много кондиционеров.

Связи: `Brand 1:N Product` и `Category 1:N Product`. Внешние ключи защищают производителя и категорию от удаления, пока на них ссылаются товары.

## REST API и CRUD

Для каждой сущности предусмотрены операции чтения списка и отдельной записи, создания, частичного обновления и удаления. Основные маршруты:

- `/api/products` и `/api/products/:id`;
- `/api/brands` и `/api/brands/:id`;
- `/api/categories` и `/api/categories/:id`;
- `/health` для проверки работоспособности процесса.

Каталог поддерживает фильтрацию по поисковой строке, производителю, категории, диапазону цены и наличию.

## Соответствие методологии 12 факторов

### I. Кодовая база

У приложения одна кодовая база. Frontend, backend, миграции и документация версионируются совместно. Разные окружения запускают один и тот же исходный код с разной конфигурацией.

### II. Зависимости

Все зависимости явно объявлены в `package.json` корневого workspace и двух приложений. Версии фиксируются в `package-lock.json`. Для установки достаточно выполнить `npm install`; код не предполагает наличия глобально установленных npm-пакетов.

### III. Конфигурация

Адрес PostgreSQL, порт backend, разрешённый origin и адрес API поступают через переменные окружения. Секреты не находятся в исходном коде. Файл `.env.example` документирует необходимые параметры, а `.env` исключён из Git.

### IV. Сторонние службы

PostgreSQL рассматривается как подключаемый ресурс. Backend получает полную строку подключения из `DATABASE_URL`, поэтому локальную базу можно заменить управляемым экземпляром без изменения кода.

### V. Сборка, релиз, выполнение

Сборка (`npm run build`), конфигурирование релиза переменными окружения и выполнение (`npm start`) разделены. Результаты сборки создаются заранее в каталогах `dist`. Миграции выполняются отдельной командой релиза, а не при каждом старте процесса.

### VI. Процессы

Backend не хранит пользовательское состояние в памяти или на локальном диске. Долговременные данные находятся в PostgreSQL. Любой экземпляр API может обработать очередной запрос.

### VII. Привязка портов

Express самостоятельно публикует HTTP-сервис на порту, который задаётся переменной `PORT`. Поэтому приложение не зависит от конкретного внешнего веб-сервера и может быть подключено к маршрутизации окружения выполнения.

### VIII. Параллелизм

API является stateless, поэтому число backend-процессов можно увеличить горизонтально и поместить за балансировщиком. Процесс не использует локальные сессии и блокировки, привязанные к одному экземпляру.

### IX. Утилизируемость

Сервис быстро запускается и обрабатывает `SIGTERM` и `SIGINT`: перестаёт принимать новые соединения, закрывает пул PostgreSQL и завершает процесс. Предусмотрен принудительный таймаут завершения через 10 секунд.

### X. Сходство сред разработки и эксплуатации

В разработке и production используются Node.js, PostgreSQL, единый `package-lock.json` и одинаковые миграции. Различаются только команды запуска и значения конфигурации. Зависимости и схема данных между окружениями не подменяются альтернативными технологиями.

### XI. Журналирование

HTTP-журнал и диагностические сообщения выводятся в `stdout`/`stderr`. Приложение не создаёт и не ротирует файлы логов. Сбором, хранением и поиском логов должно заниматься окружение выполнения.

### XII. Административные процессы

Миграции (`npm run db:migrate`) и заполнение демонстрационными данными (`npm run db:seed`) запускаются как отдельные одноразовые процессы с тем же кодом и конфигурацией, что и основной backend.

## Запуск

Полный порядок запуска и перечень команд находятся в `README.md`. Для локального запуска нужны Node.js 22+, PostgreSQL и переменные окружения из `.env.example`.
